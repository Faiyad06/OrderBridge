# OrderBridge technical design

## 1. Architecture

```
Browser (React + TS, Vite build)
   │  HttpOnly session cookie + X-CSRF-Token, same origin
   ▼
FastAPI (backend/app/main.py) ── Origin check, CSRF check, session → Actor(user, tenant, role)
   ├─ services/workspace.py   business inputs, evidence, CSV staging/commit, corrections, version bumps
   ├─ services/analysis.py    stored forecast runs, comparisons, conditions, financing, decision envelope
   ├─ services/actions.py     sandbox bootstrap, prepare → approve → execute, policy checks, receipts
   ├─ services/export.py      audit log, evidence JSON/ZIP/CSV
   ├─ agent/tools.py          7 bounded tools + JSON-schema validation, tool log
   └─ agent/orchestrator.py   replay (deterministic) or live Anthropic tool loop with budgets
          │
          ▼
   domain/engine.py, money.py, csv_import.py — pure functions, integer minor units
          │
          ▼
   SQLite (WAL, BEGIN IMMEDIATE for writes)  data/orderbridge.sqlite3
```

Domain arithmetic never imports HTTP, the database or the model SDK. Services pass plain dataclasses (`BusinessInputs`, `LedgerEvent`, `Settlement`) into the engine. In production mode FastAPI also serves `frontend/dist`. In development, Vite proxies `/api` to the backend.

## 2. Data flow for the reference journey

1. **Load synthetic example** stages `fixtures/cash_events.csv` and `fixtures/order_ORDER-001.csv` through the same import path as a user CSV, then commits each. Each commit creates a new input version (v1 → v3).
2. **Evidence** lists each record with its original row values beside the normalized values. A correction runs `PATCH /api/records/{id}` with an optimistic `record_version`, writes `record_edits` (old, new, actor, time), bumps the input version and cancels pending approvals.
3. **Compare** (`POST /api/comparisons`) runs the six scenarios and stores one `forecast_runs` row per scenario. The decision envelope is built only from those stored results.
4. **Conditions.** `POST /api/scenarios/{id}/conditions` records owner acceptance (who and when). It bumps the input version, because the terms status is part of what an approval binds to.
5. **Sandbox.** `POST /api/sandbox/initialize` requires both conditions to be accepted. It seeds the isolated account from `fixtures/sandbox_bootstrap.json`, with settlements for the deposit, the day-1 receipt and the day-2 payment. The result must reconcile to CNY 176,000.
6. **Prepare → approve → execute** (section 6). The receipt shows 176,000 → 106,000. The settlement is linked to `ORD-001-MAT-1`, so the forecast does not count that payment again.

## 3. Money, time and evidence conventions

- All persisted and API amounts are integers in minor units (CNY 1 = 100). `parse_amount_minor` uses `Decimal`. It rejects formulas, signs, exponents, thousands separators and more than two decimal places instead of rounding them.
- Interest is `principal × rate × days / basis`, computed with `Decimal` and rounded **once** with `ROUND_HALF_UP`: 110000 × 0.12 × 43 / 365 = 1555.07.
- Business dates are synthetic, with day 0 = 2026-10-01 (Asia/Shanghai) and an inclusive horizon to 2026-11-16 (day 46). Approval expiry and audit times are UTC, generated by the injectable `db.clock`.
- Confirmation status is one of `synthetic`, `assumed` (scenario terms), `parsed_unconfirmed`, `user_confirmed` or `missing`. A missing date or amount is stored as NULL, never as zero.
- The frontend only formats numbers. It never recomputes balances.

## 4. Engine formulas

For a scenario ledger L, with opening cash O on day 0:

```
closing(d) = closing(d-1) + Σ inflows(d) − Σ outflows(d),   closing(-1) = O, day-0 events included
lowest = min closing(d)  (ties → earliest date)
required_support = max(0, buffer − lowest)
first_negative = first d with closing(d) < 0;  first_buffer_breach = first d with closing(d) < buffer
contribution = Σ order inflows − Σ order outflows  (replacement events keep the order_id)
contribution_after_financing = contribution − interest − fees
```

**Settlements.** For each event, `outstanding = amount − Σ linked settlements`. The engine books each settlement on its actual date and books the outstanding remainder on the scheduled date. That way an obligation is counted exactly once (for example, a 10,000 obligation with a 4,000 settlement leaves 6,000 outstanding).

**Horizon.** If any modeled event falls after the requested horizon, the engine either extends the horizon and records an assumption, or (with `extend_horizon=false`) rejects the request.

**Incomplete inputs.** A missing date or amount produces a critical issue. The result is then `complete=false`, `terms_status=incomplete` and decision `needs_information`, and policy check `plan_cash_policy` fails, so no action can be authorised.

## 5. Scenario transformations (`fixtures/scenarios.json`)

| Scenario | Transformation | Conditions |
|---|---|---|
| no_order | drop events with an `order_id` | — |
| current_terms | base + order events | — |
| buyer_deposit | **replace** ORD-001-RCPT with ORD-001-DEP (66,000, day 0) + ORD-001-RCPT-BAL (154,000, day 45) | buyer_deposit_30pct |
| supplier_deferral | **replace** ORD-001-MAT with ORD-001-MAT-1 (70,000, day 3) + ORD-001-MAT-2 (70,000, day 46) | supplier_deferral_50pct |
| combined_terms | both replacements (by reference) | both |
| illustrative_loan | add LOAN-DRAW 110,000 day 3; LOAN-REPAY 110,000, LOAN-INTEREST 1,555.07, LOAN-FEE 500 on day 46 | credit_eligibility (fixed `not_assessed`) |

Replacements remove the original event, so a changed payment is never added on top of the original schedule. `terms_status` takes one of four values:

- `no_conditions`: the scenario has no conditions.
- `conditional`: at least one condition is unresolved.
- `accepted`: every condition has been accepted by the owner.
- `incomplete`: a critical input is missing.

Credit eligibility can never be accepted (the API returns 403 `POLICY_BLOCKED`).

**Financing assessment.** Each product is checked against purpose, currency and amount bounds. Its timing is checked by simulating a draw of the funding need on the first buffer-breach date, repaid at the earlier of the maximum term or the horizon. The product passes only if that simulation keeps the buffer. Credit approval is always `not_assessed`.

## 6. Action state machine and policy gateway

```
prepared ─► awaiting_approval ─► approved ─► executing ─► succeeded
    │               │                │            (same DB transaction)
    └► blocked      ├► cancelled     ├► expired / blocked / cancelled
                    └► blocked (input/account/policy change)
```

**Prepare.** `POST /api/actions/prepare` builds the canonical payload: action_id, tenant_id, action_type, recipient_id, obligation_event_id, amount_minor, currency, simulated_execution_date, scenario_id, financial_run_id, input_version, account_id, account_version and policy_version. The payload is serialised as sorted-key JSON and hashed with SHA-256, then stored **immutably**. Policy checks run straight away, and a failing action is stored as `blocked` with its reasons. The idempotency key is unique per tenant. Reusing it with the same request returns the existing action; reusing it with a different request returns `IDEMPOTENCY_CONFLICT`.

**Approve.** Owner only, with CSRF. The body must carry the payload hash the owner reviewed. The server recomputes the hash and checks the input, account and policy versions. The approval row binds actor, hash and policy version, with `expires_at = now + 600 s`. No model tool can reach this route.

**Execute.** One `BEGIN IMMEDIATE` transaction does the following, in order:

1. Load the action, scoped to the tenant.
2. If it has already succeeded, return the stored receipt (a status check never repeats the payment).
3. Check that the request's idempotency key matches the action.
4. Require state `approved` and an active approval.
5. Check approval expiry.
6. Recompute the hash and compare it with both the stored and the approved hash.
7. Check the input, account and policy versions.
8. Re-run every policy check, including a fresh projection of the selected plan.
9. Deduct the balance (`WHERE ledger_version = ?`), add a ledger entry, insert the settlement (unique per action), write the receipt, consume the approval and write the success audit record.

Every rejection writes the terminal state and an audit record, then returns the error. Competing executions serialise on SQLite's reserved lock. The losers then see `succeeded` and return the same receipt (covered by an 8-thread test).

**Policy checks** (proposed demo policy `demo-policy-1`, not legal or bank requirements):

- `action_type_allowed`: only `sandbox_supplier_payment`. Red operations (real payment, real borrowing, FX, adding recipients, changing limits) are rejected with 403.
- `currency`: CNY only.
- `recipient_allowlisted`: the recipient must be on this tenant's seeded allowlist.
- `per_payment_limit`: CNY 100,000.
- `daily_outgoing_limit`: CNY 120,000 per simulated day.
- `available_cash_and_buffer`: the payment must leave at least CNY 20,000 in the sandbox account.
- `plan_conditions_accepted`: every condition of the selected plan is accepted.
- `plan_cash_policy`: the recalculated plan is complete and its lowest balance is at or above the buffer.
- `obligation_outstanding`: the amount does not exceed what is still owed on the obligation.
- `recipient_matches_obligation`: the recipient is the obligation's counterparty.

## 7. Agent and provider mode

**Tools.** The agent has seven tools: `get_business_summary`, `list_evidence`, `run_forecast`, `compare_scenarios`, `list_financing_options`, `prepare_sandbox_payment` and `execute_approved_sandbox_action`. A server-side `submit_decision` tool carries the final envelope. Every input is validated against its JSON schema (types, enums, patterns, `additionalProperties: false`). There are no shell, SQL, URL or code tools.

**Execution scope.** `execute_approved_sandbox_action` is offered only in an `execute_approved` task. The owner starts that task, and the server first verifies that the action is approved. The tool then receives only the action ID, and the gateway rechecks everything.

**Budgets.** At most 8 model turns, 12 tool calls and 200k characters per request, with a 60-second request timeout. Exhausting the budget returns a labelled partial result.

**Replay.** A fixed sequence (summary → evidence issues → compare → financing if needed → prepare if accepted) runs against the same tools. It is labelled "Rule-based replay, no live model".

**Live.** The live adapter runs a manual `messages.create` tool loop (`claude-opus-5-5`, effort `medium`, optional beta refusal fallback). It appends full response blocks to the conversation and logs response IDs, stop reasons, usage and tool names. It does not log hidden reasoning. If the provider fails, the API returns `PROVIDER_UNAVAILABLE` and the run is stored with that status. It never falls back to replay silently.

**Fact checking.** The model's `submit_decision` is accepted only if:

- every `fact_ref` points at a run created in this agent run and at a real metric;
- every number of 1,000 or more in the summary matches an amount from those runs or the policy;
- its `decision_code` equals the deterministic one.

Otherwise the envelope is flagged `model_output_error`, and the summary is replaced by the calculation-based explanation.

## 8. Persistence and tenancy

SQLite runs in WAL mode with foreign keys on. There are unique constraints on `(tenant_id, idempotency_key)`, one settlement per action, and one active sandbox per tenant. Every query carries `tenant_id` taken from the session, never from the request body. Lookups that miss across tenants return the same 404 `"… not found."`, so they do not reveal that the record exists.

## 9. API error shape

`{code, user_message, field_errors?, request_id}`. The codes are:

- `VALIDATION_ERROR`, `MISSING_EVIDENCE`, `VERSION_CONFLICT`
- `APPROVAL_REQUIRED`, `APPROVAL_EXPIRED`
- `POLICY_BLOCKED`, `RECIPIENT_NOT_ALLOWED`, `INSUFFICIENT_CASH`, `IDEMPOTENCY_CONFLICT`
- `PROVIDER_UNAVAILABLE`, `UNAUTHENTICATED`, `FORBIDDEN`, `CSRF_FAILED`, `NOT_FOUND`
